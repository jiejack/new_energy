## 1. 代码审查概述

### 1.1 目的

代码审查（Code Review）是 NEM 项目保障代码质量的关口，旨在：

- **发现缺陷**：在合并前发现逻辑错误、安全漏洞、性能隐患。
- **传递知识**：促进团队成员对系统全貌的理解，避免知识孤岛。
- **统一规范**：确保代码风格、架构分层、接口契约的一致性。
- **持续改进**：通过审查反馈驱动代码质量与可维护性提升。

### 1.2 审查原则

| 原则 | 说明 |
|------|------|
| 对事不对人 | 审查针对代码而非作者，反馈客观、建设性 |
| 小步快审 | 单次审查范围控制在可一次完整审阅的粒度，避免大范围散弹式 diff |
| 证据优先 | 提出问题须指明具体代码位置与依据，避免主观臆断 |
| 阻塞与建议区分 | 阻塞问题（必须修改）与建议（可选优化）明确区分 |

### 1.3 适用范围

本规范适用于所有合并至 `dev` 分支及主分支的代码变更，包括后端（Go）、前端（Vue 3）及基础设施配置变更。

## 2. 审查流程

### 2.1 四阶段审查流程

NEM 采用四阶段审查流程，逐级递进：

```
提交前自审 → 同伴审查 → 高级审查 → 合并
```

| 阶段 | 执行者 | 职责 | 产出 |
|------|-------|------|------|
| 提交前自审 | 代码作者 | 对照审查清单自检，确保静态检查与测试通过 | 自检通过的 PR |
| 同伴审查 | 同级开发者 | 审查业务逻辑、代码规范、测试覆盖 | 审查意见 |
| 高级审查 | 高级工程师 / 技术负责人 | 审查架构合理性、安全性、性能、跨模块影响 | 审批结论 |
| 合并 | 仓库管理员 | 确认所有阻塞问题解决、CI 通过后合并 | 合并提交 |

### 2.2 提交前自审

作者在提交 PR 前须完成自审，自检清单：

- [ ] 代码通过本地静态检查（`golangci-lint` / `ESLint`）。
- [ ] 代码通过本地测试（`go test ./...` / `vitest run`）。
- [ ] 新功能已配套测试，覆盖率达标。
- [ ] 提交信息遵循 Conventional Commits 规范。
- [ ] diff 仅包含任务所需改动，无无关变更（对应 karpathy-guidelines 准则三）。
- [ ] 已更新相关文档（文档先行原则）。

### 2.3 同伴审查

- 审查人应在 1 个工作日内响应。
- 审查聚焦：业务逻辑正确性、代码可读性、测试有效性、规范一致性。
- 意见须明确标注"阻塞"或"建议"。

### 2.4 高级审查

- 聚焦架构层面：分层依赖是否正确、接口契约是否合理、是否引入循环依赖。
- 评估安全性与性能影响。
- 评估跨模块影响范围。

### 2.5 合并

- 所有阻塞问题解决且评审人确认。
- CI 流水线全部通过（`.github/workflows/ci.yml`）。
- 合并方式优先采用 Squash Merge，保持提交历史整洁。

## 3. 审查清单

### 3.1 安全性

- [ ] 是否存在 SQL 注入风险（拼接 SQL 语句）？
- [ ] 是否存在 XSS 风险（前端未转义输出）？
- [ ] 是否存在 CSRF 风险（缺少 CSRF Token）？
- [ ] 认证授权是否完备（接口是否需要鉴权）？
- [ ] 敏感数据是否脱敏（日志、响应中是否泄露密钥/密码）？
- [ ] 用户输入是否做了校验与转义？

### 3.2 性能

- [ ] 是否存在 N+1 查询（循环内查数据库）？
- [ ] 是否存在内存泄漏（goroutine 泄漏、未关闭资源）？
- [ ] 大数据集是否分页处理？
- [ ] 热点数据是否合理缓存？
- [ ] 是否存在不必要的全表扫描（缺少索引）？

### 3.3 可靠性

- [ ] 错误是否被正确处理（无吞错误、无忽略 error）？
- [ ] 资源是否正确释放（defer Close、context 取消）？
- [ ] 边界条件是否覆盖（空值、零值、越界）？
- [ ] 并发访问是否安全（共享变量是否加锁）？
- [ ] 外部依赖失败是否有降级/重试策略？

### 3.4 可维护性

- [ ] 命名是否清晰表达意图？
- [ ] 函数是否过长、复杂度过高（建议单函数不超过 50 行）？
- [ ] 是否存在重复代码（DRY 原则）？
- [ ] 注释是否解释"为什么"而非"做什么"？
- [ ] 是否符合分层架构（API → Application → Domain ← Infrastructure）？

### 3.5 架构

- [ ] 分层依赖是否单向（外层依赖内层，禁止反向）？
- [ ] 接口契约是否与既有规范一致（API 路径前缀 `/api/v1`）？
- [ ] 是否引入了不必要的抽象层或新依赖（对应准则二简单优先）？
- [ ] 模块边界是否清晰，职责是否单一？
- [ ] 变更是否影响既有接口的向后兼容性？

## 4. Go 代码审查要点

### 4.1 并发安全

```go
// ❌ 错误：共享变量未加锁
type Counter struct {
    count int
}
func (c *Counter) Inc() { c.count++ }

// ✅ 正确：使用原子操作或互斥锁
type Counter struct {
    mu    sync.Mutex
    count int
}
func (c *Counter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.count++
}
```

审查要点：
- 共享可变状态必须加锁或使用 `sync/atomic`。
- goroutine 须有明确的生命周期管理（context 取消、channel 关闭），避免泄漏。
- 使用 `go test -race` 检测数据竞争。

### 4.2 错误处理

```go
// ❌ 错误：吞错误
result, _ := doSomething()

// ❌ 错误：错误信息丢失
if err != nil {
    return errors.New("操作失败")
}

// ✅ 正确：包装错误并保留上下文
if err != nil {
    return fmt.Errorf("创建用户失败: %w", err)
}
```

审查要点：
- 禁止吞错误（`_ =` 忽略 error 返回值）。
- 错误须包装上下文信息，使用 `%w` 保留错误链。
- 使用 `pkg/errors` 统一错误码，返回结构化错误。
- 区分业务错误与系统错误，分别处理。

### 4.3 资源管理

```go
// ✅ 正确：defer 关闭资源
func readFile(path string) ([]byte, error) {
    f, err := os.Open(path)
    if err != nil {
        return nil, err
    }
    defer f.Close() // 确保资源释放
    return io.ReadAll(f)
}
```

审查要点：
- 文件、数据库连接、HTTP 响应体等资源须 `defer Close()`。
- context 须在函数间传递，支持超时与取消。
- 避免在循环中创建未释放的资源。

### 4.4 GORM 使用

```go
// ❌ 错误：N+1 查询
for _, user := range users {
    db.First(&user.Profile, user.ProfileID)
}

// ✅ 正确：预加载
db.Preload("Profile").Find(&users)
```

审查要点：
- 避免循环内查询数据库，使用 `Preload` 或批量查询。
- 查询须指定所需字段，避免 `SELECT *`。
- 写操作须在事务中执行（`db.Transaction`）。
- 软删除与硬删除策略是否符合业务预期。

### 4.5 context 传递

```go
// ❌ 错误：未传递 context
func (s *UserService) Get(id int64) (*User, error) {
    return s.repo.FindByID(context.Background(), id) // 无法取消
}

// ✅ 正确：传递调用方 context
func (s *UserService) Get(ctx context.Context, id int64) (*User, error) {
    return s.repo.FindByID(ctx, id)
}
```

审查要点：
- 所有 I/O 操作（数据库、HTTP、RPC）须接受并传递 context。
- 禁止使用 `context.Background()` 替代调用方 context（除非在入口处）。
- context 须携带超时与取消信号。

## 5. 前端代码审查要点

### 5.1 TypeScript 类型安全

- 禁止滥用 `any`，必要时使用 `unknown` 并做类型收窄。
- 接口类型定义须与后端 API 响应一致（`web/src/api/` 与 `web/src/types/`）。
- 开启严格模式，无隐式 `any`。

### 5.2 组件设计

- 组件采用 `<script setup>` 组合式 API。
- Props 须定义类型与默认值，复杂类型使用 `defineProps<T>()`。
- 组件职责单一，避免"上帝组件"。
- 公共组件抽取至 `web/src/components/`，复用而非重复。

### 5.3 状态管理

- 全局状态使用 Pinia（`web/src/stores/`），组件局部状态使用 `ref`/`reactive`。
- 避免在多个 store 间重复存储同一数据。
- 异步状态须处理 loading / error / success 三态。

### 5.4 性能与可访问性

- 列表使用 `v-for` 时须提供稳定的 `:key`。
- 大列表考虑虚拟滚动。
- 图片使用懒加载（项目已实现 `directives/lazyload.ts`）。
- 交互元素须支持键盘操作与 ARIA 属性。

## 6. 安全审查要点

### 6.1 SQL 注入

- 禁止字符串拼接 SQL，使用 GORM 参数化查询或预编译语句。
- 审查所有 `db.Raw()`、`db.Exec()` 调用，确保参数化。

### 6.2 XSS（跨站脚本）

- 前端禁止使用 `v-html` 渲染未转义的用户输入。
- Vue 默认转义插值，但 `v-html` 与 `innerHTML` 须重点审查。

### 6.3 CSRF（跨站请求伪造）

- 状态变更接口（POST/PUT/DELETE）须校验 CSRF Token 或 SameSite Cookie。
- API 须校验 `Origin` / `Referer` 头。

### 6.4 认证授权

- 除显式公开接口外，所有 API 须经过 JWT 鉴权中间件。
- 权限校验须在 Handler 层与 Service 层双重校验（防绕过）。
- Token 须设置合理过期时间，支持刷新机制。

### 6.5 敏感数据

- 密码须使用 `pkg/auth` 哈希存储，禁止明文。
- 日志中禁止打印密码、Token、密钥等敏感信息。
- API 响应中敏感字段须脱敏（如用户列表不返回密码字段）。
- 配置文件中的密钥须通过环境变量或 Nacos 注入，禁止硬编码。

## 7. 审查工具配置

### 7.1 golangci-lint（后端）

配置文件：`.golangci.yml`，在 CI 与本地均执行。

```bash
# 本地运行
golangci-lint run ./...

# CI 中运行（.github/workflows/ci.yml）
```

审查覆盖：未使用代码、错误处理、命名规范、并发安全、性能等。

### 7.2 ESLint + Prettier（前端）

配置文件：`web/.eslintrc.cjs`、`web/.prettierrc`。

```bash
# 本地运行
cd web && npm run lint

# 自动修复
npm run lint -- --fix
```

审查覆盖：代码风格、TypeScript 类型、Vue 最佳实践、未使用变量等。

### 7.3 gitleaks（密钥扫描）

配置文件：`.gitleaks.toml`，扫描代码与提交历史中的敏感信息泄露。

```bash
# 本地运行
gitleaks detect --source .

# CI 中运行（.github/workflows/security.yml）
```

### 7.4 Git Hooks

项目配置 git hooks（`scripts/git-hooks/`），在提交前自动执行检查：

| Hook | 作用 |
|------|------|
| pre-commit | 提交前运行静态检查 |
| commit-msg | 校验提交信息规范（Conventional Commits） |
| pre-push | 推送前运行测试 |

## 8. 审查常见问题与解决方案

### 8.1 问题：PR 过大无法有效审查

**解决方案**：
- 拆分为多个小 PR，每个聚焦单一职责。
- 单 PR 控制在 400 行变更以内（对应准则三精准修改）。
- 大重构须先提交设计文档与实施计划。

### 8.2 问题：审查意见含糊不清

**解决方案**：
- 意见须指明文件、行号与具体问题。
- 提供修改建议或示例代码。
- 区分"阻塞"（必须改）与"建议"（可选）。

### 8.3 问题：审查周期过长

**解决方案**：
- 同伴审查须在 1 个工作日内响应。
- 紧急修复可申请加急审查通道。
- 避免在 PR 中堆积无关讨论，离题讨论移至 Issue。

### 8.4 问题：静态检查与人工审查重复

**解决方案**：
- 静态检查能覆盖的问题（格式、命名）交由工具处理。
- 人工审查聚焦工具无法判断的：业务逻辑、架构设计、安全性。
- CI 流水线拦截静态检查未通过的 PR，减少人工负担。

### 8.5 问题：测试缺失或无效

**解决方案**：
- PR 须包含新功能的测试代码。
- 审查时验证测试是否真正覆盖了被测逻辑（而非仅调用函数）。
- 参照 `docs/skills/testing-skills.md` 的测试规范。

## 9. 审查质量标准

### 9.1 审查完成标准

一个 PR 满足以下全部条件方可合并：

- [ ] 作者自审完成，自检清单全部通过。
- [ ] 至少一名同伴审查通过，无未解决阻塞意见。
- [ ] 高级审查通过（涉及架构变更时必须）。
- [ ] CI 流水线全部通过（lint、test、build、security）。
- [ ] 新功能已配套测试且覆盖率达标。
- [ ] 相关文档已同步更新。
- [ ] 提交信息符合 Conventional Commits 规范。

### 9.2 审查人行为标准

- 审查意见客观、具体、建设性，对事不对人。
- 阻塞意见与建议明确区分标注。
- 在约定时限内响应审查请求。
- 对自己提出的阻塞意见负责跟进至解决。

### 9.3 审查效果度量

| 指标 | 目标 |
|------|------|
| 审查响应时长 | 同伴审查 ≤ 1 个工作日 |
| 审查发现的缺陷逃逸率 | 审查阶段发现 ≥ 80% 缺陷 |
| 合并后回退率 | ≤ 5% |
| PR 平均大小 | ≤ 400 行变更 |
