## 1. 审查概述

### 1.1 审查目的

本报告旨在对新能源监控系统（NEM）核心功能完善项目的需求规格说明书进行系统性审查，识别需求中的缺陷、遗漏、不一致和不可行之处，确保需求的完整性、一致性、可行性和可测试性，为后续开发工作奠定坚实基础。

### 1.2 审查范围

本次审查覆盖以下范围：

- **产品需求文档（PRD）**：`.trae/specs/nem-core-features/spec.md` 中定义的 6 项功能需求（FR-1 ~ FR-6）和 5 项非功能需求（NFR-1 ~ NFR-5）
- **实施计划**：`.trae/specs/nem-core-features/tasks.md` 中定义的 11 项任务
- **验证清单**：`.trae/specs/nem-core-features/checklist.md` 中定义的 25 项检查点
- **代码实现**：涵盖 64 个 Go 包，横跨 API 层、应用层、领域层、基础设施层和工具包层
- **测试体系**：单元测试、集成测试、性能测试和端到端测试

### 1.3 审查方法

| 方法 | 说明 |
|------|------|
| **文档审查** | 对 PRD、任务计划、验证清单进行逐项审查 |
| **代码审查** | 对核心模块源码进行静态分析，识别已知缺陷和潜在风险 |
| **测试分析** | 评估测试覆盖率、测试完整性和测试有效性 |
| **架构审查** | 评估分层架构的合理性和模块间依赖关系 |
| **缺陷追踪** | 汇总已知 Bug、TODO/FIXME 标记和技术债务 |

## 3. 需求一致性审查

### 3.1 模块间需求冲突

| 编号 | 冲突描述 | 涉及模块 | 严重程度 | 详细说明 |
|------|----------|----------|----------|----------|
| C-01 | 时间戳管理策略不一致 | lifecycle / entity | 高 | `CleanupPolicy`、`CleanupTask`、`CleanupLog` 使用 `gorm:"autoCreateTime"` 标签，但 `CreatePolicy()` 方法又手动设置 `CreatedAt = time.Now()`，导致 GORM 自动时间戳覆盖手动设置值。`AlarmRule` 实体则不使用 `autoCreateTime`，手动管理时间戳，两套策略并存 |
| C-02 | 告警规则启用/禁用实现不一致 | alarm_rule_handler / alarm_rule_service | 中 | `EnableAlarmRule` 和 `DisableAlarmRule` Handler 直接调用 `UpdateRule` 方法而非专用的 `EnableRule`/`DisableRule` Service 方法，绕过了状态检查逻辑 |
| C-03 | 错误响应码不一致 | 多个 Handler | 中 | 部分 Handler 对业务错误返回 500（如 `CreateAlarmRule` 中规则名重复返回 500），应返回 409 Conflict；`DeleteAlarmRule` 对删除失败统一返回 404，但实际可能是数据库错误 |
| C-04 | 分页参数处理不一致 | alarm_rule_handler / alarm_rule_repository | 低 | Handler 层未对 `page` 和 `page_size` 做边界校验，Repository 层直接使用，可能产生负数偏移量 |
| C-05 | 导出服务职责重叠 | export_service / report_service | 中 | `ReportService` 内部实现了 `exportExcel` 和 `exportCSV` 方法，与 `ExportService` 的职责重叠，违反 DRY 原则 |

### 3.2 需求与实现不一致

| 编号 | 不一致描述 | 严重程度 | 详细说明 |
|------|------------|----------|----------|
| CI-01 | Station Handler 全部为空实现 | 高 | `station_handler.go` 中 15 个方法全部为 `// TODO: 实现`，仅返回空响应，与 FR-6 前后端集成需求严重不符 |
| CI-02 | Region Handler 全部为空实现 | 高 | `region_handler.go` 中 5 个方法全部为空实现 |
| CI-03 | Point Handler 全部为空实现 | 高 | `point_handler.go` 中 5 个方法全部为空实现 |
| CI-04 | 规则引擎核心方法为简化实现 | 中 | `rule/engine.go` 中 `evaluateCondition` 始终返回 `true`，`executeFormula` 仅支持简单变量引用，`executeExpression` 返回 0，`executeScript` 仅求和，与生产级要求差距大 |
| CI-05 | 流式导出未真正分批 | 中 | `StreamExportAlarms` 声称支持大数据量分批导出，但实际仍一次性查询全部数据 |
| CI-06 | 配置中心加载未实现 | 低 | `config/loader.go` 中 Nacos/Apollo/Consul/Etcd 配置加载均为 TODO |

### 3.3 数据模型不一致

| 编号 | 不一致描述 | 严重程度 | 详细说明 |
|------|------------|----------|----------|
| DM-01 | 时间戳字段策略不统一 | 高 | 部分实体使用 `gorm:"autoCreateTime"`（lifecycle 包 12 处、qa.go 2 处、config.go 4 处、system_config.go 1 处），部分实体手动管理时间戳（alarm_rule.go、device.go），策略不统一导致维护困难和潜在 Bug |
| DM-02 | ID 生成策略不统一 | 中 | 部分实体在 Service 层生成 UUID（alarm_rule_service.go），部分在 Repository 层依赖数据库自增，部分在实体构造函数中生成 |
| DM-03 | 软删除策略缺失 | 中 | 告警规则、设备等核心实体使用硬删除，缺少软删除（`gorm.DeletedAt`）支持，数据无法恢复 |

## 4. 需求可行性审查

### 4.1 技术可行性

| 编号 | 需求 | 可行性评估 | 风险等级 | 详细说明 |
|------|------|------------|----------|----------|
| T-01 | DryRun 模式数据清理 | ❌ 不可行 | 高 | `cleanup.go` 的 `doCleanup` 方法中，当 `DryRun=true` 时，循环内仅累加 `totalDeleted` 但不删除数据，下一轮查询会返回相同的记录，导致**无限循环**。必须在 DryRun 模式下跳过循环或使用游标推进 |
| T-02 | GORM autoCreateTime 冲突 | ⚠️ 有风险 | 高 | 使用 `gorm:"autoCreateTime"` 的实体在代码中手动设置 `CreatedAt` 值时，GORM 会覆盖手动值，导致时间戳不一致。影响范围：lifecycle 包 12 处、qa.go 2 处、config.go 4 处 |
| T-03 | SQL 注入风险 | ⚠️ 有风险 | 高 | `CleanupOrphanedRecords`、`CleanupDuplicates`、`VacuumTable`、`ReindexTable`、`AnalyzeTable` 等方法使用 `fmt.Sprintf` 拼接 SQL，存在 SQL 注入风险 |
| T-04 | 规则引擎表达式执行 | ⚠️ 有风险 | 中 | `evaluateCondition` 始终返回 `true`，`executeFormula` 仅支持简单变量引用，无法满足生产级告警规则配置需求 |
| T-05 | 大数据量导出 | ⚠️ 有风险 | 中 | `StreamExportAlarms` 声称流式导出但实际一次性加载全部数据，10 万条以上数据可能导致内存溢出 |
| T-06 | WebSocket 并发安全 | ⚠️ 有风险 | 中 | `Hub.BroadcastToStation` 和 `BroadcastToUser` 在 `RLock` 内修改 map（`delete`），违反 Go map 并发安全规则，可能导致 panic |
| T-07 | 协程池并发安全 | ⚠️ 有风险 | 中 | `WorkerPool` 的 `workers` map 在 `addWorker`、`dispatchTask`、`cleanIdleWorkersOnce` 中并发读写，缺少互斥锁保护 |
| T-08 | 数据清理循环内频繁 DB 查询 | ⚠️ 有风险 | 中 | `checkTaskCancelled` 在每次循环迭代中查询数据库，`doCleanup` 每批都执行 `dc.db.Save(task)` 更新进度，高频率 DB 操作影响性能 |

### 4.2 资源可行性

| 编号 | 资源需求 | 可行性评估 | 风险等级 | 详细说明 |
|------|----------|------------|----------|----------|

| R-02 | 测试人力 | ⚠️ 不足 | 中 | 23 个包测试覆盖率为 0%，补全测试需要大量人力投入 |

### 4.3 进度可行性

| 编号 | 进度风险 | 风险等级 | 详细说明 |

### 9.2 关键发现

1. **5 项严重缺陷需立即修复**：DryRun 无限循环、GORM 时间戳覆盖、WebSocket 并发安全、WorkerPool 并发安全、SQL 注入漏洞。这些缺陷可导致系统崩溃、数据不一致或安全漏洞。

2. **3 个核心模块完全未实现**：Station Handler、Region Handler、Point Handler 全部为 TODO 空实现，直接影响 FR-6 前后端集成需求的交付。

3. **需求文档存在 3 项未决问题**：PRD 中的 Open Questions（报表自定义时间段、PDF 导出、规则版本管理）未得到解决，影响需求完整性。

4. **测试覆盖率严重不足**：估算整体覆盖率约 67%，23 个包覆盖率为 0%，与 NFR-3 要求的 ≥80% 存在较大差距。

5. **技术债务积累较多**：36 处 TODO/FIXME 标记、时间戳管理策略不统一、规则引擎核心方法为占位实现等，需要系统性清理。
