## 1. 测试策略概述

### 1.1 测试目标

新能源监控系统（NEM）作为面向光伏、风电、储能场景的工业物联网监控平台，对系统可靠性、实时性与数据准确性有极高要求。本测试计划旨在：

1. **保障功能正确性**：验证所有功能模块符合需求规格
2. **保障系统稳定性**：确保系统在长时间运行、高并发、异常输入下稳定运行
3. **保障数据准确性**：验证工业协议采集、时序数据存储、计算结果的准确性
4. **保障性能达标**：验证系统满足工业场景的实时性与吞吐量要求
5. **保障安全合规**：验证认证、授权、数据安全符合工业安全标准

### 1.2 测试金字塔

本计划遵循测试金字塔模型，按 70/20/10 比例分配测试用例：

```
            /\
           /  \
          / E2E\         10% - 端到端测试（验收级）
         /------\
        / 集成  \        20% - 集成测试（模块间）
       /--------\
      /  单元    \       70% - 单元测试（函数级）
     /------------\
```

| 层级 | 占比 | 用例数（预估） | 执行频率 | 反馈速度 |
|------|------|---------------|----------|----------|
| 单元测试 | 70% | ~3500 | 每次提交 | 秒级 |
| 集成测试 | 20% | ~1000 | 每日构建 | 分钟级 |
| 端到端测试 | 10% | ~500 | 发布前 | 小时级 |

### 1.3 测试原则

1. **测试左移**：需求阶段即定义验收标准，开发阶段同步编写测试
2. **快速反馈**：单元测试 < 10s，集成测试 < 5min，E2E < 30min
3. **隔离性**：测试之间相互独立，可任意顺序执行
4. **可重复性**：相同输入产生相同结果，避免依赖时间、网络、外部状态
5. **真实数据**：使用脱敏后的生产数据样本，提升测试有效性
6. **缺陷预防**：通过测试发现的设计缺陷反哺需求与设计

### 1.4 测试范围

**包含范围**：
- 后端：所有 Go 包（api、application、domain、infrastructure、pkg/*）
- 前端：Vue 组件、Store、Router、API 调用
- 协议层：IEC 104、Modbus、IEC 61850 采集与解析
- 数据层：PostgreSQL、Redis、Kafka、ClickHouse/Doris
- AI 模块：负荷预测、故障诊断、RUL、RAG、智能问答
- 部署：Docker、Kubernetes 配置验证

**排除范围**：
- 第三方库内部实现
- 操作系统内核
- 硬件设备固件

#### 2.2.2 测试规范

**命名规范**：
```go
// 函数: Test<被测函数>_<场景>
func TestCreateStation_WhenNameExists_ShouldReturnError(t *testing.T)

// 表驱动测试
func TestParseModbusFrame(t *testing.T) {
    tests := []struct {
        name    string
        input   []byte
        want    *Frame
        wantErr bool
    }{
        // ...
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            // ...
        })
    }
}
```

**断言规范**：
- 使用 `testify/assert` 进行断言
- 错误信息包含上下文：`assert.Equal(t, expected, actual, "设备ID=%s 解析失败", deviceID)`
- 避免使用 `fmt.Println` 调试，使用 `t.Logf`

**隔离规范**：
- 每个测试用例独立构造依赖，不共享全局状态
- 使用 `t.Cleanup()` 清理资源
- 数据库测试使用事务回滚或独立 Schema
- 时间相关逻辑使用 `clock.NewFake()` 或接口注入

#### 2.2.3 分层测试策略

| 层级 | 测试重点 | Mock 策略 | 覆盖率要求 |
|------|----------|-----------|-----------|
| Handler 层 | 参数校验、路由、响应格式 | Mock Service | ≥ 80% |
| Service 层 | 业务逻辑、事务、编排 | Mock Repository | ≥ 80% |
| Repository 层 | SQL、查询、持久化 | sqlmock / testcontainers | ≥ 80% |
| Domain 层 | 实体逻辑、值对象、领域服务 | 无 Mock（纯逻辑） | ≥ 90% |
| pkg 工具包 | 协议解析、算法、工具函数 | 无 Mock（纯逻辑） | ≥ 85% |

#### 2.2.4 关键模块测试要点

**协议解析（IEC 104 / Modbus / IEC 61850）**：
- 使用真实报文样本作为输入
- 覆盖正常帧、异常帧、截断帧、超长帧
- 验证字节序、位序、时间戳解析
- 覆盖所有功能码与异常码

**告警引擎**：
- 规则匹配：阈值、窗口、聚合
- 状态机：触发、确认、恢复、抑制
- 通知渠道：邮件、短信、Webhook（Mock 外部服务）
- 并发场景：多规则同时触发、去重

**AI 模块**：
- 模型推理：使用固定输入验证输出范围
- RAG 检索：Mock 向量数据库
- 提示词模板：变量替换、上下文截断
- 边缘计算：心跳、模型同步、数据预处理

```go
func setupIntegrationEnv(t *testing.T) (*sql.DB, redis.Client, *kafka.Client) {
    t.Helper()
    // 启动 PostgreSQL 容器
    pgContainer, pgDB := startPostgres(t)
    // 启动 Redis 容器
    redisContainer, redisClient := startRedis(t)
    // 启动 Kafka 容器
    kafkaContainer, kafkaClient := startKafka(t)
    
    t.Cleanup(func() {
        pgContainer.Terminate(ctx)
        redisContainer.Terminate(ctx)
        kafkaContainer.Terminate(ctx)

}
```

## 8. 测试数据管理

### 8.1 测试数据来源

| 来源 | 用途 | 管理方式 |
|------|------|----------|
| Factory 生成 | 单元测试 | 代码内 Factory 函数 |
| Fixture 文件 | 集成测试 | `tests/fixtures/` 目录 |
| 脱敏生产数据 | 系统测试 | 数据脱敏脚本 |
| 模拟设备数据 | 协议测试 | 协议模拟器生成 |

### 8.2 测试数据原则

1. **可重复**：相同测试数据可多次使用，结果一致
2. **隔离性**：测试数据不跨用例共享，避免相互影响
3. **真实性**：使用贴近真实的数据分布，提升测试有效性
4. **合规性**：生产数据必须脱敏，符合数据安全规范
5. **可维护**：数据生成逻辑集中管理，避免散落各处

### 8.3 测试数据生命周期

```
生成 → 使用 → 清理
 │       │       │
Factory  测试    t.Cleanup()
         执行    事务回滚
```

### 8.4 敏感数据处理

- 禁止在测试代码中硬编码真实密码、Token、密钥
- 使用环境变量或测试专用配置文件管理敏感信息
- 生产数据脱敏规则：姓名、手机号、地址、设备序列号
- 脱敏数据存放在独立加密存储，访问需审批

## 9. 持续集成中的测试

### 9.1 CI 流水线测试阶段

```yaml
stages:
  - lint          # 代码风格检查
  - unit-test     # 单元测试 + 覆盖率
  - security      # 安全扫描
  - build         # 构建镜像
  - integration   # 集成测试（main 分支）
  - e2e           # E2E 测试（发布前）
  - performance   # 性能测试（定期）
```

### 9.2 测试执行策略

| 阶段 | 触发 | 并行度 | 超时 | 失败处理 |
|------|------|--------|------|----------|
| Lint | PR | 1 | 5min | 阻断 |
| 单元测试 | PR | 4 | 10min | 阻断 |
| 安全扫描 | PR | 1 | 10min | 阻断 |
| 集成测试 | main 合并 | 2 | 30min | 阻断 |
| E2E 测试 | Release 分支 | 1 | 60min | 阻断发布 |
| 性能测试 | 每周 / Release | 1 | 120min | 警告 + 报告 |

### 9.3 测试报告

- **覆盖率报告**：Codecov / Codecov.io 集成，PR 中展示覆盖率变化
- **测试结果**：JUnit XML 格式，CI 平台可视化
- **性能报告**：k6 结果输出到 Grafana，趋势对比
- **缺陷报告**：自动创建 Issue，关联失败用例

### 9.4 Flaky 测试治理

1. **识别**：CI 标记重试通过的用例为 Flaky
2. **跟踪**：Flaky 测试清单，每周评审
3. **修复**：48h 内修复或隔离
4. **预防**：根因分析，补充最佳实践
