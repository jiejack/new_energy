## 1. 阶段目标与范围

### 1.1 阶段主题

**测试覆盖与质量提升**：在第一阶段（W1-W4）完成核心功能开发的基础上，本阶段聚焦于系统质量保障体系建设，通过系统化的测试补齐与质量门禁建设，将所有包的测试覆盖率提升至 80% 以上，建立可持续的质量保障机制。

### 1.2 阶段目标

| 序号 | 目标 | 量化指标 | 验收方式 |
|------|------|----------|----------|
| G1 | 全包测试覆盖率达标 | 所有包覆盖率 ≥ 80% | `go test -cover` 报告 |
| G2 | 关键路径集成测试覆盖 | 核心业务流程 100% 覆盖 | 集成测试报告 |
| G3 | 质量门禁上线 | CI 流水线强制门禁生效 | CI 流水线配置 |
| G4 | 缺陷修复 | P0/P1 缺陷清零 | 缺陷跟踪系统 |
| G5 | 性能基线建立 | 核心接口 P99 ≤ 200ms | 性能测试报告 |

### 1.3 阶段范围

**包含范围（In Scope）**：
- 现有所有 Go 包的单元测试补齐
- 关键业务流程的集成测试编写
- 前端核心组件的单元测试与 E2E 测试补齐
- CI/CD 质量门禁配置
- 测试基础设施完善（Mock、Fixture、Factory）
- 已知缺陷修复

**排除范围（Out of Scope）**：
- 新功能开发（推迟至 Phase 3）
- 大规模架构重构
- 性能深度优化（推迟至 Phase 4）
- 生产环境部署

### 1.4 阶段原则

1. **测试先行**：修复缺陷与补齐测试优先于新功能
2. **质量门禁**：未达覆盖率的代码不允许合并
3. **分层覆盖**：单元测试为主，集成测试为辅，端到端测试兜底
4. **可重复性**：所有测试可在 CI 环境一键执行

## 3. 测试覆盖率提升计划

### 3.1 当前覆盖率状态（基线）

| `internal/infrastructure/persistence` | 43.6% | 80% | 36.4% | P0 | 见 3.2.3 |

### 3.2 分包提升策略

#### 3.2.1 `pkg/nacos`（8.5% → 80%）

**问题分析**：配置客户端与服务发现注册器几乎无测试，依赖外部 Nacos 实例。
**提升策略**：
1. 引入 `nacos-mock` 接口抽象，剥离对真实 Nacos 的依赖
2. 为 `config_client.go` 编写配置读取、监听、变更回调测试
3. 为 `health_check.go` 编写健康检查、超时、重试测试
4. 为 `registry.go` 编写服务注册、注销、心跳测试
5. 使用 `testify/mock` 生成 Mock 对象

#### 3.2.2 `internal/api/handler`（37.8% → 80%）

**问题分析**：23 个 Handler 中仅部分有测试，边界条件与错误路径覆盖不足。
**提升策略**：
1. 统一 Handler 测试模板（Gin `httptest` + Mock Service）
2. 每个 Handler 必须覆盖：正常路径、参数校验失败、权限不足、Service 错误、未找到资源
3. 优先补齐 `asset_*`、`cost_*`、`carbon_emission`、`energy_efficiency` 等无测试 Handler
4. 引入表驱动测试（table-driven test）减少重复代码

#### 3.2.3 `internal/infrastructure/persistence`（43.6% → 80%）

**问题分析**：仓储层测试依赖真实数据库，事务与并发场景未覆盖。
**提升策略**：
1. 使用 `sqlmock` 或测试容器（testcontainers）隔离数据库依赖
2. 覆盖 CRUD、分页查询、事务回滚、唯一约束冲突
3. 为 `migration.go` 编写迁移幂等性、回滚测试
4. 为 `database.go` 编写连接池、健康检查、重连测试

#### 3.2.4 `pkg/monitoring/alerting`（47.5% → 80%）

**问题分析**：告警聚合、通知、规则引擎核心逻辑测试不足。
**提升策略**：
1. 为 `aggregator.go` 编写窗口聚合、去重、合并测试
2. 为 `notifier.go` 编写邮件、短信、Webhook 通知测试（Mock 外部服务）
3. 为 `rules.go` 编写规则匹配、阈值判断、抑制规则测试
4. 为 `service.go` 编写告警生命周期测试

#### 3.2.5 `pkg/collector/modbus`（48.6% → 80%）

**问题分析**：Modbus 协议解析与异常处理测试缺失。
**提升策略**：
1. 为协议编解码编写字节级单元测试（使用真实报文样本）
2. 为异常码处理编写测试（IllegalFunction、IllegalDataAddress 等）
3. 为连接超时、读写重试编写测试
4. 引入 Modbus 从站模拟器进行集成测试

#### 3.2.6 `pkg/storage/query`（50.4% → 80%）

**问题分析**：查询执行器、缓存、限流测试不足。
**提升策略**：
1. 为 `executor.go` 编写查询计划、执行、结果合并测试
2. 为 `cache.go` 编写缓存命中、失效、淘汰策略测试
3. 为 `ratelimit.go` 编写令牌桶、突发限流测试
4. 为 `monitor.go` 编写查询指标采集测试

#### 3.2.7 `pkg/compute/rule/scheduler`（53.0% → 80%）

**问题分析**：调度器、触发器、分布式锁测试不足。
**提升策略**：
1. 为 `scheduler.go` 编写 Cron 表达式解析、任务调度测试
2. 为 `trigger.go` 编写事件触发、条件触发测试
3. 为 `lock.go` 编写分布式锁获取、释放、续约、竞争测试
4. 使用 `clock.NewFake()` 控制时间相关逻辑

#### 3.2.8 `pkg/storage/timeseries`（56.7% → 80%）

**问题分析**：多后端（ClickHouse、Doris）适配与批量写入测试不足。
**提升策略**：
1. 为 `batch_writer.go` 编写批量聚合、刷新、失败重试测试
2. 为 `factory.go` 编写后端选择、配置加载测试
3. 为 `clickhouse.go`、`doris.go` 编写 SQL 生成、查询执行测试（Mock 驱动）
4. 为 `errors.go` 编写错误分类、重试策略测试

#### 3.2.9 `pkg/websocket`（60.6% → 80%）

**问题分析**：并发场景与连接管理测试不足。
**提升策略**：
1. 为 `hub.go` 编写连接注册、注销、广播测试（含并发场景）
2. 为 `handler.go` 编写握手、消息收发、心跳测试
3. 为 `realtime.go` 编写实时数据推送、订阅管理测试
4. 使用 `race detector` 验证并发安全

#### 3.2.10 `pkg/ai/service`（61.0% → 80%）

**问题分析**：AI 服务适配层与上下文管理测试不足。
**提升策略**：
1. 为 `adapter.go` 编写多模型适配、错误转换测试
2. 为 `context.go` 编写上下文构建、截断、合并测试
3. 为 `prompt.go` 编写提示词模板、变量替换测试
4. 为 `interface.go` 编写接口契约测试

## 4. 质量门禁标准

### 4.1 代码质量门禁

| 门禁项 | 阈值 | 工具 | 阻断级别 |
|--------|------|------|----------|
| 单元测试覆盖率（全包） | ≥ 80% | `go test -cover` | 阻断合并 |
| 单元测试通过率 | 100% | `go test` | 阻断合并 |
| Lint 检查 | 0 error | `golangci-lint` | 阻断合并 |
| 安全扫描 | 0 高危 | `gosec` / `gitleaks` | 阻断合并 |
| 代码复杂度（圈复杂度） | ≤ 15 | `gocyclo` | 警告 |
| 重复代码率 | ≤ 5% | `jscpd` | 警告 |

### 4.2 前端质量门禁

| 门禁项 | 阈值 | 工具 | 阻断级别 |
|--------|------|------|----------|
| 单元测试覆盖率 | ≥ 70% | Vitest | 阻断合并 |
| 单元测试通过率 | 100% | Vitest | 阻断合并 |
| Lint 检查 | 0 error | ESLint | 阻断合并 |
| 类型检查 | 0 error | `tsc --noEmit` | 阻断合并 |
| 包大小 | ≤ 2MB（gzip） | `vite build` | 警告 |

### 4.3 集成测试门禁

| 门禁项 | 阈值 | 工具 | 阻断级别 |
|--------|------|------|----------|
| 集成测试通过率 | 100% | `go test -tags=integration` | 阻断合并 |
| E2E 测试通过率 | ≥ 95% | Playwright | 阻断发布 |
| API 契约一致性 | 100% | OpenAPI 校验 | 阻断合并 |

### 4.4 门禁执行流程

```
PR 提交
  ├─ 1. 代码风格检查（gofmt / eslint）
  ├─ 2. Lint 检查（golangci-lint / eslint）
  ├─ 3. 单元测试 + 覆盖率检查
  ├─ 4. 安全扫描（gosec / gitleaks）
  ├─ 5. 集成测试（仅 main 分支）
  ├─ 6. E2E 测试（仅发布前）
  └─ 7. 代码评审（≥ 1 人 approve）
       └─ 合并
```
